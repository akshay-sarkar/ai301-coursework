# Rubric: is this plan ready to post and build from?

Grade the plan, not the polish. A terse plan that names its cause, its one change, and an observable test is ready; a long confident plan that blames something the evidence rules out, or bundles a redesign around the fix, is not. Every check reads the plan against the issue, the repro evidence, the thread, or the repo facts, never against its own length or headings.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| grounded-diagnosis | The plan's stated cause (diagnosis / root-cause section), read against every step, control run, and artifact in the repro-evidence block (see evidence guide: Diagnosis and grounding) | Pass if the stated cause is consistent with every artifact in the repro evidence, including control runs and "works when X" observations. Fail if any control, step, or artifact shows the blamed component, layer, or step working correctly, or shows the symptom already present before the blamed step runs; or if the plan adopts a cause (its own, or a confident one from the thread) that the repro evidence rules out; or if the plan states no cause at all. | required |
| bounded-scope | The plan's scope / in-scope / not-in-scope statements and its approach, read against what the issue and repro evidence ask for (see evidence guide: Scope) | Pass if the plan makes one bounded change aimed at the reproduced behavior, and any wider work (refactors, migrations, new options, rewrites, test-harness changes, other symptoms) is either absent or named as deferred / out of scope. A plan that is honestly scoped down (defers part of the issue and says why) passes. Fail if the plan commits to work the issue never asked for alongside the fix: a rewrite or restructure, a dependency/runtime migration, a new user-facing option or feature, a framework, a CI change, or "while I'm in the area" work. | required |
| executable | The plan's files / areas, approach, and order of work (see evidence guide: Executability) | Pass if a stranger could start the build without asking the author anything: the plan names the file(s) or function(s) to change and commits to one approach. Fail if no file or area is named, if the approach is still a choice ("X or Y, whichever is easier", "gocui? tcell? not sure", "recover() somewhere"), or if the first step is to investigate / profile / poke around before any change is decided. | required |
| decisive-test | The plan's test plan, read against the repro evidence's trigger and observed symptom (see evidence guide: Test plan) | Pass if the test plan re-runs the reproduced trigger (or a regression test built from it) and names the observable outcome expected after the fix (an exit code, an output, a value, a rendered result, a test that now passes). Fail if the only test is "run the full test suite", "CI passes", "should feel fast", "nothing else should break", or any check with no observable outcome tied to the reproduced behavior. | required |
| thread-aware | The plan comment and plan, read against the thread-highlights block (maintainer/OWNER/MEMBER comments, linked PRs, prior art) (see evidence guide: Comms) | Pass if the thread has no maintainer direction or prior art, or the plan comment engages it: it follows the maintainer's stated direction or isolated culprit, or names it and says why the plan differs; and it acknowledges any open PR or posted patch instead of racing or ignoring it. Fail if a maintainer has named a culprit, a direction, or a patch to test and the plan comment neither follows nor addresses it (e.g. a docs-only workaround when the owner has isolated a code fix and asked for testing). | required |
| repo-conventions | The contribution-policy line in the repo-facts block (live: CONTRIBUTING.md, AI_POLICY.md, AGENTS.md), read against the plan comment. Treat every package as AI-assisted work. (see evidence guide: Comms) | Pass if no AI policy is stated, or the policy puts no disclosure requirement on comments, or the plan comment meets the stated requirement (names the tool and extent of AI help where all AI usage must be disclosed; human-voiced where the policy asks for the contributor's own words). Fail if the policy requires disclosing AI usage that covers comments or "any form" of use and the plan comment does not disclose it. | required |
| honest-unknowns | The plan's risks / unknowns section and any certainty words in the plan or comment (see evidence guide: Honesty) | Pass if what the plan has not verified is stated as an unknown or risk rather than asserted as fact, and no delivery date or guaranteed outcome is promised. | preferred |

## Verdict rule

- accept only if every `required` check passes.
- `unclear` on a `required` check counts as fail, except: `thread-aware` is graded pass (never unclear) when the thread highlights contain no maintainer direction, prior art, or open PR; `repo-conventions` is graded pass (never unclear) when no AI policy is stated.
- `preferred` checks are reported but never change the verdict.
- Otherwise reject.

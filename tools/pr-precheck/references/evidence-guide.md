# Evidence guide: where evidence lives in a PR package

An eval bundle has these parts, in order: `## Repo facts` (including the `pull requests:` line with the PR template's asks, and the contribution-policy line), `## Issue`, `## Thread highlights`, `## Plan context` (the plan's scope, approach, test plan, and deviation notes), and `## Candidate PR` with `### Title`, `### Description`, `### Commits`, `### Diff`, and `### Test evidence`. In live mode the same evidence lives in the student's working copy and on GitHub: `plan.md` (with `## Deviations`), the branch's diff from `git diff main...HEAD`, the draft title and description in `pr_draft.md`, the captured output in `test_evidence.md`, and the repo's `.github/PULL_REQUEST_TEMPLATE.md` and `docs/CONTRIBUTING.md`.

## Plan fidelity (harness category: silent-drift)

- Where it lives: eval, the scope / in-scope / out-of-scope lines, approach, and deviation notes in `## Plan context`, read against the hunks in `### Diff`, and the claims in `### Title` and `### Description` read against that same diff. Live, `plan.md` (Scope, Files, Approach, and `## Deviations`) against `git diff main...HEAD`, and `pr_draft.md` against the diff.
- What good looks like: every changed file and hunk is something the plan names or a deviation note records, and every planned change is in the diff or explicitly deferred. Silent drift runs both ways. "More than the plan" is an unrequested rewrite, a new option or flag, a rename pass, or an edit to a file the plan never touches. "Less than the plan" is a planned docs update or second fix that's missing with no note. A description that claims "exactly as planned", "no changes beyond the plan", or a change the diff doesn't contain is drift too, however polished. An honest deferral, recorded in the plan's notes and restated in the description, is not drift.

## Test evidence (harness category: not-tested)

- Where it lives: eval, `### Test evidence` in `## Candidate PR`, read against the test plan in `## Plan context` and the reproduction trigger in `## Issue`. Live, `test_evidence.md` against the Test plan section of `plan.md` and the student's posted repro.
- What good looks like: for every failure mode the plan's test plan names, the issue's own trigger (or a regression test built from it) is re-run, with the failing output before and the expected output after, pasted. The repo's own checks are shown with their results (for Path Review: `make test-unit`, `make test-integration`, `make lint`, `make typecheck`), and a failing or "no tests ran" result is reported honestly with its reason. Not decisive: "tested locally", "works on my machine", "cargo test passes" with no output, a run of the control or an unchanged path (the single-file case that never broke, a GET when the bug is in POST), or re-running one of two named failure modes and staying silent on the other.

## Diff quality (harness category: unreviewable)

- Where it lives: eval, the unified diff in `### Diff` and the messages in `### Commits`. Live, `git diff main...HEAD` and `git log main..HEAD --oneline`.
- What good looks like: the fix is visible and nothing else rides along. Debris tells: a debug print or `eprintln`, a commented-out line or a commented-out first attempt, a dead function (often behind an `allow(dead_code)` or with an `_unused` name), a TODO left on an unrelated line, import reordering, re-indent or whitespace churn in lines the fix doesn't need, and identical lines removed and re-added. Commit messages like "wip", "fix", or "misc cleanups while debugging" usually point at debris in the diff. Any one debris hunk makes the diff unreviewable, even around a correct fix.

## Standards and comms (harness category: standards-wall)

- Where it lives: eval, the `pull requests:` and contribution-policy lines in `## Repo facts`, plus maintainer comments in `## Thread highlights`, read against `### Description` and `### Diff`. Live, `.github/PULL_REQUEST_TEMPLATE.md`, `docs/CONTRIBUTING.md`, any AI_POLICY.md or AGENTS.md, and the issue thread, read against `pr_draft.md` and the diff.
- What good looks like: every section the template asks for has real content, the required issue link is present (`Closes #N`), required checklist items and artifacts are actually there (a whatsnew or changelog entry in the diff, tests added, a seeded bug's xfail marker and any matching pyproject suppression removed), ticked boxes are backed by evidence, and a maintainer's direction or question in the thread is engaged. On AI use, treat every package as AI-assisted: where the policy requires disclosure, the description names the tool and how it was used, in the contributor's own words. Visible failures: no `Closes #`, an empty or boilerplate checklist, a required artifact missing from the diff, or no disclosure under a policy that requires one, however good the fix is. Whether the description's claims match the diff belongs to plan fidelity, not here.

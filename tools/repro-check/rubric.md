# Rubric: is this reproduction package ready to post?

Read the whole package (issue, claim comment, repro report) before grading. Grade the proof, not the polish: every check reads the artifact or the words against the issue itself, never the length, headings, or confidence of the write-up. "Artifact" means output, logs, exit codes, or screenshots that are actually pasted in the package; a sentence describing output is not an artifact.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| env-recorded | The repro report's environment record, read against the version and platform the issue targets and the bug-report template asks in the repo-facts block (see evidence guide: Environment) | Pass if the report names the tool/library version (or commit SHA) AND the OS/platform it ran on, plus any setting the issue says the failure depends on (driver, build profile, shell, config). If the version or platform differs from the one in the issue, the report states the difference in words. Fail if there is no environment record, if a setting the issue depends on is missing, or if the version/platform silently differs from the issue's. | required |
| same-trigger | The repro report's steps, command, and input, compared character-for-character with the trigger in the issue body (see evidence guide: Steps) | Pass if the command and input match the issue's trigger, or every difference is named in the report with a reason. Fail if the input, syntax, flags, or operator silently differ from the issue's (e.g. `:` for `=`, a prefix range for an offset-from-end range, a modified expression), or if the steps skip the trigger. | required |
| steps-rerunnable | The repro report's steps, from starting state to trigger (see evidence guide: Steps) | Pass if a stranger with only the package could run every step: the commands are shown exactly, and each input file is either pasted or described precisely enough to recreate (its keys, sections, or contents named, e.g. "a valid `dependencies:` list plus a `category:` section"). Fail if any step depends on private code, an unshared or undescribed config, a setting the issue depends on that is left out, or an unexplained step like "set up the project". | required |
| behavior-shown | Pasted artifacts in the repro report, read against the behavior the issue describes (error type, message, exit code, crash vs graceful error) (see evidence guide: Behavior shown) | Pass if (a) a pasted artifact shows the same symptom the issue describes (same error class and message, or same wrong output), OR (b) the report is a cannot-reproduce whose pasted artifacts come from running the issue's exact trigger and show the symptom absent. Fail if no artifact is pasted, if the artifact shows a different symptom (a graceful validation/syntax error where the issue reports a crash or panic, a compile error where the issue reports a runtime error, the program simply running normally), or if the artifact contradicts the report's own narration. | required |
| claims-backed | The report's headline outcome (reproduced / cannot reproduce / confirmed / root cause) and any claim of testing on another version, machine, or release, in the repro report and the claim comment, each matched to a pasted artifact (see evidence guide: Honesty) | Pass if the headline outcome rests on a pasted artifact, and every other assertion is either shown, a precise observation stated alongside that artifact (a control run's result, a "behavior unchanged" note on the version the artifact came from), or hedged as a hypothesis ("suggests", "looks like", "likely"). An honest cannot-reproduce that shows its attempt and names what differed passes. Fail if the headline outcome has no pasted artifact behind it, a root cause is stated as verified with no transcript, results are claimed for a version/machine/release other than the one the artifact came from, or certainty words ("guaranteed", "confirmed on two machines") rest on nothing shown. | required |
| claim-specific | The claim comment read against the issue (see evidence guide: Comms) | Pass if the claim names something specific to this issue (the behavior, error, file, or trigger) AND states a concrete next step (reproduce, investigate a named area, report back). Fail if it is interchangeable boilerplate that could sit on any issue ("assign me", "+1", "I can take this"), or if it promises a fix, a guaranteed outcome, or a delivery date. | required |
| repo-conventions | The contribution policy line in the repo-facts block (live: CONTRIBUTING.md, AI_POLICY.md, AGENTS.md), read against the claim comment and repro report. Treat every candidate package as AI-assisted work. (see evidence guide: Comms) | Pass if the repo states no AI policy, or its policy puts no disclosure requirement on issue comments, or the comments meet the stated requirement (e.g. disclose the tool and extent of AI use where disclosure of all AI usage is required; written in the contributor's own words where that is what the policy asks). Fail if the policy requires disclosure of AI usage that covers comments or "any form" of use and neither comment discloses it. If the repo-facts block does not mention a policy at all, grade pass. | required |
| control-run | The repro report's artifacts (see evidence guide: Behavior shown) | Pass if the report includes a control or comparison run (a nearby input that behaves correctly, or the issue's expected output) that isolates the trigger. | preferred |

## Verdict rule

- accept only if every `required` check passes.
- `unclear` on a `required` check counts as fail, with two exceptions: (1) in a claim-only live draft, checks whose evidence is the repro report are reported `unclear` / "not yet applicable: claim-only draft" and are left out of the verdict; (2) `repo-conventions` is graded pass, never unclear, when no policy is stated.
- `preferred` checks never change the verdict.
- Otherwise reject.
